# AI 总结流式输出性能修复

日期：2026-10-08。针对“AI 总结流式输出太慢”，在已确认的同屏工作区、会员额度和 DeepSeek 调用规则上优化本机开销。

## 原因与实测

旧代码在模型 SSE 的每行数据及每次草稿更新时检查任务。会员启用后，每次检查还会打开额度数据库；一次模型输出片段通常包含数据行和空行，因此同一片段重复打开多个 SQLite 连接。小片段密集到达时，接收线程被本机数据库访问阻塞。每段模型请求还单独创建 HTTP 客户端和 TLS 上下文。

使用隔离学习库及隔离会员库，模拟相同的完整 JSON，总长 **6,817 字符**，每次输出 4 字符，共 **1,705 个片段**。模型由 `httpx.MockTransport` 提供，没有网络等待、真实模型调用或费用。模拟使用真实的任务检查、会员预留到期检查、草稿解析和阶段存储。

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 本机接收、解析和草稿更新 | 103,988.2 ms | 947.0 ms |
| 模型接收路径任务检查回调 | 3,416 次 | 11 次 |
| 草稿回调 | 1,705 次 | 1,705 次 |
| 返回完整内容与模拟输入一致 | 是 | 是 |

本机处理开销下降约 **99.1%**。修复前草稿回调内部另有 1,705 次检查，未计入上表的模型接收回调计数。独立的默认 TLS 客户端创建测量为约 0.8–1.4 秒／次，受本机状态影响。

该测量不代表真实视频能在一秒内完成总结。字幕获取、模型排队、首字等待、生成速率、长视频的分段及最终汇总仍会占用时间。本轮没有新增真实模型生成；需要用户在实际服务验收输出速度。

## 实现与边界

- `deepseek_client.py`：流接收期间按 100 ms 间隔检查任务和预留到期状态；每个模型片段继续立即触发草稿回调，完整内容照常累积。请求前、最终响应处理、缓存写入及正式保存前仍分别执行检查。没有数据到达时仍受原网络读取超时约束。
- `analysis_jobs.py`：摘要草稿只更新受锁保护的内存状态，不逐片段查询数据库。删除记录与清除草稿使用同一把锁，迟到文字不能恢复已删除的任务。
- 模型 HTTP 连接池由学习引擎持有，分段、汇总、重试及后续任务共享连接。配置、凭据、用量回调仍属于各自任务；显式请求不合并连接池中的 cookie。请求保留证书验证、禁止跳转及原来不读取系统代理的行为；获取连接池和首次 TLS 初始化纳入原截止时间。
- 流响应在成功、重试和失败时均关闭；任务自有的模拟／独立客户端在结束时释放，共享连接池在引擎关闭时释放。

摘要提示词、模型、分段顺序、输出预算、引用验证、缓存指纹、最多一次结构修复、网络断流不自动重发、会员额度和下载规则保持原行为。没有减少正文、丢弃后段内容、增加模型并发或新增自动计费请求。

连接池实现查阅了 Context7 的 `/encode/httpx` 文档，并核对 [HTTPX 官方客户端说明](https://www.python-httpx.org/advanced/clients/) 的连接复用、显式请求和关闭规则。

## 人工验收
